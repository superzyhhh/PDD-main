# 工程技能组使用指南（skills/）

> 给 agent 的入口文档：**先读本文件定位技能，再只读那一个 `SKILL.md`**。不要一次性通读全部技能，也不要预先加载参考文档。

## 1. 这是什么

`skills/` 是一组 **Markdown 形式的技能**（指令 + 参考知识），不是可执行代码。一个技能 = `skills/<name>/SKILL.md`（含 `name` / `description` frontmatter）+ 可选同目录参考文档。

本仓库已完成初始化，**通常不需要再运行 `setup-matt-pocock-skills`**：

- `AGENTS.md` 记录了 issue tracker、分诊标签、领域文档三条配置
- `docs/agents/issue-tracker.md`：本地 Markdown tracker（`.scratch/`）
- `docs/agents/triage-labels.md`：五个分诊标签
- `docs/agents/domain.md`：`CONTEXT.md` + `docs/adr/` 的消费规则

## 2. 调用约定

本仓库的技能**没有注册为平台技能**，所以“调用”= 用 Read 打开对应文件并照做：

| 用户说法 | 实际操作 |
| --- | --- |
| 输入 `/tdd`、`/triage`，或“用 /xxx” | Read `skills/<name>/SKILL.md` |
| SKILL.md 里写“调用 `/yyy`” | Read `skills/yyy/SKILL.md` |
| 任务命中某技能的触发场景 | 读该技能的 `SKILL.md`（仅限下表的“可自主触发”） |
| 需要参考文档 | 只读该 `SKILL.md` 里指向的那一个文件 |

两类技能，区别在是否需要用户点名：

- **可自主触发**（frontmatter 无 `disable-model-invocation`）：`grilling`、`tdd`、`code-review`、`codebase-design`、`domain-modeling`。命中触发场景可直接读。
- **仅显式调用**（`disable-model-invocation: true`）：`wayfinder`、`grill-with-docs`、`to-spec`、`to-tickets`、`triage`、`implement`、`improve-codebase-architecture`、`setup-matt-pocock-skills`、`writing-great-skills`。用户没点名时不要自行启动，可以在回复里建议。

典型加载流程（以“把需求落成工单”为例）：

```
1. 读 skills/README.md（本文件）→ 定位到 to-tickets
2. Read skills/to-tickets/SKILL.md
3. 需要 tracker 约定 → Read docs/agents/issue-tracker.md
4. 需要领域词汇 → Read CONTEXT.md（及该领域的 docs/adr/*.md）
5. 不读 setup 模板，不读其他技能
```

## 3. 速查：现在要做什么 → 用哪个技能

| 场景 | 技能 | 产出 / 落点 |
| --- | --- | --- |
| 想法太大，看不清怎么走到目的地 | `wayfinder` | `.scratch/<effort>/map.md` + 决策工单 |
| 把方案拷问到清楚，并顺手沉淀文档 | `grill-with-docs`（= `grilling` + `domain-modeling`） | `CONTEXT.md`、新 ADR |
| 只想受压提问，不写文档 | `grilling` | 无文件，按轮问答 |
| 对话已聊清楚，要落成规格 | `to-spec` | `.scratch/<feature>/spec.md` |
| 规格拆成可独立交付的小工单 | `to-tickets` | `.scratch/<feature>/issues/NN-*.md` |
| 按 spec / 工单写代码 | `implement`（内含 `tdd`，收尾 `code-review`） | 代码 + 测试 + 提交 |
| 测试先行做功能或修 bug | `tdd` | 测试与最小实现 |
| 审分支 / PR / 在途改动 | `code-review` | Standards + Spec 双轴报告 |
| 找架构改进点（浅模块变深模块） | `improve-codebase-architecture` | 临时目录中的 HTML 报告 |
| 设计模块接口、决定 seam 放哪 | `codebase-design` | 只提供词汇与原则 |
| 维护 `CONTEXT.md` / ADR | `domain-modeling` | `CONTEXT.md`、`docs/adr/` |
| 收件箱 issue 分类、写 agent brief | `triage` | 标签 + brief；`.out-of-scope/` |
| 写或改技能本身 | `writing-great-skills` | 技能文件 |
| 更换 tracker / 重启配置 | `setup-matt-pocock-skills` | `docs/agents/*`（一次性） |

## 4. 标准流水线

```
wayfinder（只做规划，不做交付）
  └─→ grill-with-docs（grilling + domain-modeling）→ 更新 CONTEXT.md / ADR
       └─→ to-spec → .scratch/<feature>/spec.md
            └─→ to-tickets → .scratch/<feature>/issues/NN-*.md
                 └─→ implement（内含 tdd，收尾 code-review）→ 提交到当前分支

分诊旁路：triage → ready-for-agent + agent brief → implement
架构旁路：improve-codebase-architecture → 选中候选 → grilling → 决策 → 回到 to-tickets
```

## 5. 技能详表

| 技能 | 调用 | 核心规则 | 产出 | 附属文件（何时读） |
| --- | --- | --- | --- | --- |
| `wayfinder` | 显式 | 在 tracker 上建一张 map + 决策工单；默认**只决策不交付**；每会话最多解决一个工单（research 除外）；工单一律用标题称呼，不用编号；用“雾”记录尚说不清的问题 | `.scratch/<effort>/map.md`、`issues/NN-*.md`（`Type:` / `Status:` / `Blocked by:` 行） | 无；tracker 操作见 `docs/agents/issue-tracker.md` 的 Wayfinding 节 |
| `grilling` | 可自主 | 把决策画成设计树，按“轮”一次性问完当前可问的问题；每问编号并给出推荐答案；事实自己派子代理查，不向用户索取 | 无文件，直到用户确认达成共识 | 无 |
| `grill-with-docs` | 显式 | 只有一行：跑 `grilling` 并配合 `domain-modeling` | `CONTEXT.md`、ADR | 无 |
| `to-spec` | 显式 | 不访谈，直接综合已有对话；先确定并确认测试 seam；按七节模板写；标 `ready-for-agent` | `.scratch/<feature>/spec.md` | 无 |
| `to-tickets` | 显式 | 垂直 tracer-bullet 切片；宽重构用 expand–contract；先向用户确认拆分与阻塞关系再发布；不改/不关父 issue | `.scratch/<feature>/issues/NN-<slug>.md` | 无 |
| `implement` | 显式 | 按 spec/工单实现；用 `tdd`；常跑类型检查与单测，最后跑全量；结束用 `code-review`；提交到当前分支 | 代码、测试、提交 | 无 |
| `tdd` | 可自主 | 只测外部行为；seam 必须事先与用户约定；红先绿后；一次一片垂直切片；重构留给 review | 测试 + 最小实现 | `tests.md`（要例子时）、`mocking.md`（要 mock 时） |
| `code-review` | 可自主 | 用户给固定点（commit/tag/branch）；`git diff <point>...HEAD`；Standards 与 Spec 两轴并行子代理；**不合并、不重排**两轴结论 | 双轴报告 | 无 |
| `codebase-design` | 可自主 | 统一词汇：module / interface / depth / seam / adapter / leverage / locality；删除测试；接口即测试面；“一适配器=假 seam，两适配器=真 seam” | 无文件（词汇参考） | `DEEPENING.md`（要深化的依赖分类）、`DESIGN-IT-TWICE.md`（要并行设计多版接口） |
| `improve-codebase-architecture` | 显式 | 先看 `git log` 热点定范围；Explore 子代理找摩擦；报告写到系统临时目录并打开（Windows `%TEMP%`），**不写进仓库**；不先提接口；用户选中后再 `grilling` | 临时目录 `architecture-review-<ts>.html` | `HTML-REPORT.md`（写报告时） |
| `triage` | 显式 | 类别 `bug`/`enhancement` + 五个状态；先查重、再查 `.out-of-scope/`；验证 claim 后再 grill；`ready-for-agent` 必须附 agent brief；写入 tracker 的每条评论以 `> *This was generated by AI during triage.*` 开头 | 标签、brief、`.out-of-scope/` | `AGENT-BRIEF.md`（写 brief 时）、`OUT-OF-SCOPE.md`（拒绝 enhancement 时） |
| `domain-modeling` | 可自主 | 主动挑战与 `CONTEXT.md` 冲突的用词；术语敲定即刻写入 `CONTEXT.md`（**只放术语表**，不放实现细节）；ADR 仅在“难逆转 + 无上下文会困惑 + 真实权衡”三条全满足时建议 | `CONTEXT.md`、`docs/adr/NNNN-*.md` | `CONTEXT-FORMAT.md`（建/改术语表时）、`ADR-FORMAT.md`（写 ADR 时） |
| `writing-great-skills` | 显式 | 可预测性是首要美德；区分 model-invoked / user-invoked；控制 context load；用 leading word；逐句做 no-op 测试；避免 duplication / sediment / sprawl | 无文件（参考） | `GLOSSARY.md`（查定义时） |
| `setup-matt-pocock-skills` | 显式 | 一次性初始化；本仓库已配好，**除非要换 tracker 不要重跑** | `docs/agents/issue-tracker.md`、`triage-labels.md`、`domain.md`、AGENTS.md 的 `## Agent skills` | 各 `issue-tracker-*.md`、`domain.md`、`triage-labels.md`（仅在重配时拷模板） |

| 位置 | 作用 | 现状 |

| `CONTEXT.md` | 领域术语表（唯一语言来源） | 已存在 |
| `docs/adr/NNNN-*.md` | 架构决策记录 | 已有 0001–0009 |

| `.out-of-scope/<concept>.md` | 被拒需求的沉淀 | 尚未创建，首次拒绝 enhancement 时惰性创建 |

## 7. 硬规则（照做，不要再重新摸索）

1. **一次只加载一个 `SKILL.md`**；参考文档只在正文指针触发时读。
2. 领域命名一律使用 `CONTEXT.md` 的术语，不用它标注为 _Avoid_ 的同义词。
3. 与既有 ADR 冲突要显式写明“与 ADR-000X 冲突，但值得重开，因为……”，不要静默覆盖。
4. spec / 工单 / agent brief **不写文件路径与行号**，只写行为契约与可独立验收的标准。
5. 测试只写在事先与用户确认过的 seam，只测外部行为。
6. TDD 红先绿后，一次一片；重构不属于红绿循环，留给 review。
7. `wayfinder` 默认只产出决策；每会话最多解决一个工单（research 工单可并行）。
8. triage 往 tracker 写的每条评论都必须以 AI 生成声明开头。
9. 本地工单一工单一文件，绝不合并；不关闭、不修改父 issue。
10. 架构报告写在系统临时目录，不落进仓库。

## 8. 验证命令

| 范围 | 命令 |
| --- | --- |
| Web 单测 | `cd apps/web; npm test`（vitest run） |
| Web 类型检查 + 构建 | `cd apps/web; npm run build`（`tsc -b && vite build`） |
| Agent 测试 | `cd apps/agent; pytest` |

`implement` 要求：常跑类型检查与单个测试文件，最后跑一次全量；完成后用 `code-review` 自查“标准 + 规格”两轴。

## 9. 维护这套技能

- 改技能前先读 `writing-great-skills/SKILL.md`，遵守单一事实来源，逐句做 no-op 测试。
- 新增技能：建 `skills/<name>/SKILL.md`；需要 agent 自主触发才写面向模型的 `description`，否则加 `disable-model-invocation: true`。
- 本目录是外部工程技能集的本地副本：升级时整目录替换；**仓库特有约定写进本 README 与 `docs/agents/`，不要改 `SKILL.md`**。
- 增删技能后同步更新本文件第 3 节速查表与第 5 节详表。

## 10. 与 AGENTS.md 的关系

`AGENTS.md` 是每次都会注入的最小入口（三条配置 + 本文件指针）；本 README 是技能组路由表。agent 的顺序是：

```
AGENTS.md（常驻配置）→ 本 README（定位技能）→ 目标 SKILL.md（执行）→ 只在需要时读附属文档
```
