# 02 — 三候选与首图接受

**What to build:** 同一次生成产出三张候选（保主体细节 / 保色彩层次 / 保少色号），顺序固定，用户选一张即进入图纸详情。用户选中第一张即记录「首图接受」。同一张原图与同一参数组合重复提交命中内容寻址缓存，返回相同候选且不新增扣费。

**Status:** ready-for-human

- [ ] 三候选至少在色号数或降采样策略上互不相同，用户能看出差异（服务端已断言色号数与集合差异；真机可见性统一并入工单 12）
- [x] 选中任一张后进入图纸详情，选中第一张触发首图接受事件
- [x] 同图同参数再次提交命中缓存，返回相同候选，耗时明显下降且不重复计费（以任务复用与二次查询即刻完成验证，候选逐字段一致；未做计时断言）
- [x] 埋点事件名与字段契约确定，可被后续看板消费

## Comments

三候选由既有引擎参数组合而成，顺序固定：保主体细节为边缘感知降采样、开启抖动、色号上限放开到 221；保色彩层次为平均降采样、开启抖动、上限 64 色；保少色号为平均降采样、关闭抖动、上限 24 色。色号裁剪复用 Pindo 的调色板裁剪能力，按 ADR-0001 只在服务端运行，边界检查通过。

埋点契约为两个事件：`candidate_selected` 与 `first_pattern_accepted`，均携带 `taskId`、`candidateId`、`index`；`first_pattern_accepted` 的 `index` 恒为 0 且 `candidateId` 必须为 `detail`。时间戳由服务端补写，以 `audit` 级日志留痕。上报时服务端校验任务已完成、`index` 处的候选标识与上报一致，并在任务属于某用户时校验会话归属，非法事件回 400/403。

小程序端先展示三个候选的缩略图（标签与色号数），点选后进入详情 canvas；同一任务同一候选只上报一次，上报失败允许下次点击重试。

验证：类型检查、GPL 边界检查与 9 个服务端测试全绿。新增测试覆盖三候选顺序与统一结构契约、色号上限与集合差异、缓存复用后候选逐字段一致、埋点契约与非法事件拒绝。
